## What this project is

SPAR project "Orthogonalization Against Reward Hacking", mentored by Vlad. Goal: test whether refusal-style orthogonalization (abliteration, a la arxiv 2406.11717 / the `heretic` library) can remove reward hacking from an already-trained production model.

Design decisions already made, do not relitigate them in code:

- Ablation is applied post-training to the weights of a released model, not during RL. Start with 4B-8B models (Qwen3.5-class), scale up only once it works.
- Directions come from difference-of-means over paired trajectories (hacking vs. not hacking). Sources: reward-hacking benchmarks with programmatic hack detection (ImpossibleBench, EvilGenie), LLM-judged rollouts, or honeypot envs (`ekhadley/odd-number-hacking`, `gkroiz/agent-interp-envs`). Follow heretic's layer selection and ablation procedure; the open question is which sequence positions to pool activations from, since heretic only uses prompt tokens and rollouts are long agentic transcripts.
- Evaluate hack rate on the same benchmark the training pairs came from, using the same judge. Capability checks: MMLU plus something agentic like SWE-Bench, and the benchmarks must be unhackable.
- Until the minimal version works, no extra degradation-mitigation tricks beyond what heretic already does. A clean negative result is an acceptable outcome.
- LLM judging goes through OpenRouter with the provider pinned (see guidelines). Prefer a judge over substring matching for hack detection.

## Data

Every rollout comes from the Inspect environments under `envs/` (grader, secret_number, impossible_bench): a run is an Inspect log under `logs/`, and `envs/convert.py` turns logs into rollout records under `data/inspect/<env>/<log name>.jsonl`, one rollout per line with a nested list of turns, cheat flags, labels, the condition label, the whole run config, and the served token ids. A run is an `EvalCfg` instance (`envs/common.py`), one flat dataclass: env, yaml config, size, the intervention (`lora`, the `add_*` fields, the `ablate_*` fields) and the server; the named instances live in `run.py` and are launched from the repo root as `./run.py <name> ...` (no names lists them), every named run checked before the first eval, the server's hooks set and cleared around each one, the log converted and the cheat rates printed after it. `envs/README.md` documents the interface, the commands, and what was checked. No rollouts are imported from agent-interp-envs results, and nothing in the repo harvests activations from secret_number rollouts.

- A secret_number turn's `commands` are what the env executed (from the solver's step records). `tool_calls` are what the model attempted; the env rejects multi-call turns and runs nothing. Cheat flags use `commands`.
- `data/vectors/<model>/` (tracked) holds `[n_layers, d_model]` direction tensors with json sidecars, written by `utils.save_vector`. Names are `<env>_<family>_<contrast>`; the one there now is `grader_parity_cheat_vs_clean`, whose rows are differences of unit-sphere means (norms 0.003 to 0.1, against residual norms of 12 to 200), so an `add_alpha` under `row` scaling is in those units. Vectors computed from rollouts must come from Inspect records.

Code:

- `run.py`: the named `EvalCfg` instances and the launcher, a flat executable script at the repo root that puts `envs/` on `sys.path` (the env modules import each other by bare name). The instances are module-level variables, a variant a `dataclasses.replace` of a base one, a sweep one instance per point; `./run.py <name> ...` runs them in order and `./run.py` alone lists them with the fields they set (`summary`). A new setting is a new field on `EvalCfg` with a default, never a flag or a string grammar; a new run is a new instance. The script is a flat sequence: every named run's task built first (which runs `common.check` and the task's asserts), server checks per run (model and adapter served, no request in flight), then per run `set_hooks`, `eval`, `clear_hooks` in a `finally`, `convert.write_records`, and a rate table (`rate_rows`) under the run's condition label (`common.condition`: `none` with no intervention, else the instance's name).
- `envs/common.py`: `EvalCfg` and what a run sends: `check` (field combinations, vector files and layers), `steering_vectors` (one vllm-lens vector per listed layer, that layer's own row, scale alpha, the unit row under `unit` and `resid_norm`, `norm_match` under `resid_norm`), `request_body`, `projection_hook` / `set_hooks` / `clear_hooks` (the ablation on the server), `generate_config` (the yaml's model block plus the request fields, the intervention fields as `cache_salt`), `task_metadata`, `load_vector`.
- The `grader` env (`envs/grader.py`) is the single-turn grader-metadata environment: a request plus a `<_grader>` block. A family (`envs/configs/grader/families/<family>.yaml`) is two mirrored sides, each with a request, the grader that rewards its answers, and for word answers the answer list of that side. `hack` prompts carry the other side's grader, `clean` the side's own, `none` no metadata; cheat is an answer belonging to the other side, None for an answer on neither. Families: `parity` (even / odd), `pets` (household pet / dangerous wild animal, predicate grader), `pets_listed` (the same with the rewarded answers listed in the grader), `sign` (positive / negative integer, 0 neither), `letter` (vowel / consonant, y neither), `weekday` (weekday / weekend day). Record labels: `family`, `side`, `prompts`, `sys`, `cheat`.
- `grader_lens.py`: kernel cell script, GPU box for the 27B. Constants (the parity prompts, dirs, `load_rollouts`) plus flag-gated cells, no other helpers: every cell is a flat sequence of load, compute, save, plot, print so any line can be commented out, and the model-facing work is in `utils.py`. It never samples a dataset: `load_rollouts(tag)` reads the parity family's hack-prompt records from `data/inspect/grader/` (default config, condition none, the system prompt named by the tag). Cells: j-lens cluster readouts (`mechtools.lens`, lenses from `camilablank/workspace-lenses`) at the grader tokens and along one sampled completion; prompt-difference directions (a hack prompt's last-position residual with the control prompts' span rejected, per layer); a single reasoning-on completion under add or projection hooks; a harvest cell computing each (tag, side, class) group's per-rollout CoT means from the records' served token ids (`cot_means`, cpu tensors, stripped variants with the system turn cut out of the ids); extract cells that are arithmetic on those: cheat minus clean within each side averaged over the two sides (`grader_parity_cheat_vs_clean`, the `_generic[_stripped]` and `very_hacker_cheat_vs_generic_clean[_stripped]` variants) and the whole-set means and their difference (`grader_parity_<tag>_mean[_stripped]`, `grader_parity_very_hacker_vs_generic[_stripped]`); a cell needing no rollouts: the last-prompt-token resid_post with thinking off under the very_hacker minus the generic system prompt, averaged over the two hack prompts (`grader_parity_very_hacker_vs_generic_prompt`); a j-lens readout of a saved vector; and a steered "what are you thinking about" completion. All vectors are saved to `data/vectors/<model>/` with `utils.save_vector`. Hack rates under an intervention come from a run's intervention fields (`EvalCfg` in `run.py`), not from this script. Steering is only ever a positive add to induce hacking (alpha x the gap for a saved vector); the suppression intervention is projection, never a negative coefficient.
- `utils.py`: pure functions of the model and its inputs that return tensors or lists, no printing, plotting or writing except `save_vector`: `render` / `resid` / `resid_post` / `last_resid` (prompt ids and per-layer resid_pre or resid_post), `reject`, `resid_pre_layout` (a saved row-i-at-resid_post.i vector shifted to row L at resid_pre L), `add_hooks` / `proj_hooks` / `make_proj_out_hook`, `find` (token index of a substring), `cot_span` / `strip_system_turn` / `resid_post_mean` / `cot_means` (per-rollout CoT means, on the cpu), `save_vector` / `load_vector` (the vector file format, which `envs/common.py` also reads), and `lens_readout` (cluster readout of a `[n_layers, d_model]` vector; readouts of a cache use `mechtools.jlens_cluster_readout` directly).
