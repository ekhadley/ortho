## What this project is

SPAR project "Orthogonalization Against Reward Hacking", mentored by Vlad. Goal: test whether refusal-style orthogonalization (abliteration, a la arxiv 2406.11717 / the `heretic` library) can remove reward hacking from an already-trained production model.

Design decisions already made, do not relitigate them in code:

- Ablation is applied post-training to the weights of a released model, not during RL. Start with 4B-8B models (Qwen3.5-class), scale up only once it works.
- Directions come from difference-of-means over paired trajectories (hacking vs. not hacking). Sources: reward-hacking benchmarks with programmatic hack detection (ImpossibleBench, EvilGenie), LLM-judged rollouts, or honeypot envs (`ekhadley/odd-number-hacking`, `gkroiz/agent-interp-envs`). Follow heretic's layer selection and ablation procedure; the open question is which sequence positions to pool activations from, since heretic only uses prompt tokens and rollouts are long agentic transcripts.
- Evaluate hack rate on the same benchmark the training pairs came from, using the same judge. Capability checks: MMLU plus something agentic like SWE-Bench, and the benchmarks must be unhackable.
- Until the minimal version works, no extra degradation-mitigation tricks beyond what heretic already does. A clean negative result is an acceptable outcome.
- LLM judging goes through OpenRouter with the provider pinned (see guidelines). Prefer a judge over substring matching for hack detection.

## Data

`data/`, `acts/` and the directories under `logs/` are gitignored and live in the public HF dataset `eekay/ortho` under the same paths: `bash scripts/hf_push.sh` from the repo root uploads what is new (resumable, deletes nothing; it leaves out `acts/weights` and the downloaded copies of Will's dataset), and `hf download eekay/ortho --repo-type dataset --local-dir .` fetches it. The dataset is public, so nothing with a key or token in it goes under those directories.

Every rollout comes from the Inspect environments of the `rhenvs` package (grader, secret_number, impossible_bench, terminal_verifier, mbpp; public repo github.com/ekhadley/rh-envs, cloned at `~/wgmn/rh-envs`, shared with a project partner, installed here as a git dependency pinned in `uv.lock`): a run is an Inspect log under `logs/`, and `rhenvs.convert` turns logs into rollout records under `data/inspect/<env>/<log name>.jsonl`, one rollout per line with a nested list of turns, cheat flags, labels, every key of the log's task metadata (the task's own env, config_id and arguments, and ours: the condition label, the whole run config, the vectors dir and `envs_commit`, the rhenvs commit that ran), and the served token ids. Changing an env is a commit pushed to rh-envs, then `uv sync --upgrade-package rhenvs` here; nothing about activations or interventions lives in rhenvs. A run is an `EvalCfg` instance (`common.py`), one flat dataclass: env, yaml config, size and task fields, the intervention (`lora`, the `add_*` fields, the `ablate_*` fields) and the server; the named instances live in `run.py` and `ablations.py` (the suppression variants, imported by `run.py`) and are launched from the repo root as `./run.py <name> ...` (no names lists them), every named run checked before the first eval, the server's hooks set and cleared around each one, the log converted and the cheat rates printed after it. rh-envs's `README.md` documents the tasks, their arguments and configs, and what was checked of the envs; `README.md` here the runs, the interventions, and what was checked of them. No rollouts are imported from agent-interp-envs results, and nothing in the repo harvests activations from secret_number rollouts.

- `terminal_verifier` (`rhenvs/terminal_verifier.py`) is the mentor's TerminalVerifierEnv (JYudelson1/MonitorDecorrelation, branch spar): a largest-island grid, a terminal holding `verifier.py`, one `<command>` per turn run in rhenvs's `docker/python/` container, the history re-shown each turn. `EvalCfg.mode` is what the verifier holds (`verifier_bug`: only tampering passes; `corrupted`: reading the file and submitting its value passes; `possible`: the control), `max_turns` the command limit, `seed` the grids. Flags: passed, tampered, peeked, used_verifier, submitted_true_answer, passed_blind; cheated is tampered or passed in an impossible mode.
- `mbpp` (`rhenvs/mbpp.py`) is the mentor's MBPP-Honeypot (task text plus one visible test, the first code block run against the visible and two held-out tests) with willjgriff's impossible-visible-test variant as the yaml's `corrupt` switch: under `impossible` the visible test's expected value is wrong and passing it is the cheat (27% on Qwen3.8-27B in that sweep); under `honeypot` the cheat is a literal hardcode that fails a held-out test (0 of 200 there). The tasks are rhenvs's `configs/mbpp/tasks.jsonl` from `rhenvs/mbpp_tasks.py`; `epochs` is samples per task. An answer with no code block or cut off by max_tokens is invalid (cheat None).
- `secret_number` (`rhenvs/secret_number.py`) has two configs: `qwen3.6-27b` (the agent-interp-envs config, the one every Qwen3.6 rollout used) and `qwen3.8_low`, the same game, prompts and sampling at reasoning effort low, the setting of the Qwen3.8 runs. `secret38` in `run.py` is the Qwen3.8 base run (`cb_base`); `mbpplora_secret`, `graderlora_secret`, `mbppkto_secret` and `kto_secret` are the adapters' and the directions'. No direction or adapter is trained on it.
- A secret_number turn's `commands` are what the env executed (from the solver's step records). `tool_calls` are what the model attempted; the env rejects multi-call turns and runs nothing. Cheat flags use `commands`.
- `data/vectors/<model>/` holds `[n_layers, d_model]` direction tensors with json sidecars, written by `utils.save_vector`. Names are `<env>_<family>_<contrast>`; the one there now is `grader_parity_cheat_vs_clean`, whose rows are differences of unit-sphere means (norms 0.003 to 0.1, against residual norms of 12 to 200), so an `add_alpha` under `row` scaling is in those units. Vectors computed from rollouts must come from Inspect records.

Code:

- `run.py`: the named `EvalCfg` instances and the launcher, a flat executable script at the repo root. The instances are module-level variables, a variant a `dataclasses.replace` of a base one, a sweep one instance per point; `./run.py <name> ...` runs them in order and `./run.py` alone lists them with the fields they set (`summary`). A new setting is a new field on `EvalCfg` with a default, never a flag or a string grammar; a new run is a new instance. The script is a flat sequence: every named run's task built first (`common.build_task`, which runs `common.check` and the task's own asserts), server checks per run (model and adapter served, no request in flight), then per run `set_hooks`, `eval`, `clear_hooks` in a `finally`, `rhenvs.convert.write_records`, and a rate table (`rate_rows`) under the run's condition label (`common.condition`: `none` with no intervention, else the instance's name).
- Standard side-effect tests: every intervention gets a `<row>_none` and a `<row>_clean` run in `run.py` (all grader families, no grader and the grader that agrees with the request), compared by `common.shift_rows` against `none38` and `clean38`: valid rate, wrong-side rate, answer shift (total variation distance, beside its shuffled-label 95% noise level) and completion length. A vector with no served row gets the same table from `train_vector.py`'s side effects cell and `./side_effects.py <name>`.
- Served projection: `scripts/vllm_proj.py` is a vLLM patch applying a `train_vector.py` MODE project vector exactly (the same hook at the same layer outputs, every position, no weight edit), `scripts/proj_export.py` writes its input file, `scripts/box_proj_setup.sh` installs it and row `proj` (`cb_proj`, base weights), and `scripts/proj_check.py` scores held-out completions through a served row to compare against `train_vector.py`'s held-out gains. Will's `stage5b_ablate.py --stack` is not equivalent to this hook: it also edits the writers before the window and leaves the embedding's component. `scripts/proj_widen.py` writes `grader_proj_all`, the same direction at every decoder layer with base-model means for layers 0-29, and `scripts/box_projall.sh` runs its capability pass and serves it as row `projall` (`cb_projall`). `scripts/proj_target.py` writes a `gen_only` hook file (row `projgen`, `cb_projgen`): generated tokens only, pinned past the honest mean by a fraction of the cheat-honest gap; `scripts/proj_gen_check.py` checks such a row against the HF hook on sampled single-turn completions and scored multi-turn rollouts. `gen_only` covers the current generation and the finished assistant turns of the prompt (`vllm_proj.generated_mask`), so prompt scoring of a whole rollout reaches the hook. Row `projallgen` (`cb_projallgen`) is `grader_proj_all` under `gen_only`. `train_vector.py` with LOSS kto and GEN_ONLY writes `grader_kto`: one direction at layers 30-63, generated tokens only, pinned at the mean of the non-cheating rollouts' generated tokens, trained with cheating below the base model, honest above it, and the base `none38` and `clean38` rollouts held by token KL; it is served as row `kto` (`cb_kto`). ENV mbpp writes `mbpp_kto` the same way from base MBPP rollouts (`mbpp38`, `mbpp38_x4`), MBPP's test split held out, with `mbpp38_correct` and the Grader neutrals; its saved rows point away from cheating, which the projection ignores. `train_vector.py` with TRAIN False is the held-out screen: teacher-forced log-prob gains of same-prompt cheating and honest base rollouts under the hook, for NAME and every COMPARE direction, summed and per token of each completion (the classes differ in length, so the per-token margin is the one to read), with the neutrals' token KL and log-prob gain and each pair's gains and token counts. `scripts/dpo_screen.py` sets that screen up for the additive DPO vectors as steering and as a row-wise projection (vectors and scores in `data/vectors/Qwen3.8-27B/dpo_screen/`), and `scripts/dpo_screen_box.sh` runs it on the box. `probe_envs.py` reads saved directions on base rollouts of other envs, against random directions. `scripts/jlens_scores.py` reads a saved direction through the Qwen3.6-27B J-lens on Qwen3.8 (no 3.8 lens exists), `scripts/jlens_baseline.py` runs the same lens check on Qwen3.6 itself, and `jlens_page.py` builds the clustered page; J-lens means this trained lens, and Will's finite-difference `scripts/jlens_readout.py` is a separate readout whose outputs are in `data/vectors/Qwen3.8-27B/fd_readout/`. `proj_*`, `projall_*`, `projgen_*`, `projallgen_*`, `kto_*` and `mbppkto_*` in `run.py` are their runs.
- `common.py`: `EvalCfg` and what a run sends: `TASKS` (env name to rhenvs task function), `check` (no task field the env's task does not take, the intervention's field combinations, vector files and layers), `steering_vectors` (one vllm-lens vector per listed layer, that layer's own row, scale alpha, the unit row under `unit` and `resid_norm`, `norm_match` under `resid_norm`), `request_body`, `projection_hook` / `set_hooks` / `clear_hooks` (the ablation on the server), `build_task` (the rhenvs task called with the cfg's task fields that are set, the request fields merged into its config's extra_body with a hash of the intervention fields as `cache_salt`, which vLLM caps at 128 characters, and condition, vectors, cfg and `envs_commit` added to its metadata), `load_vector`.
- The `grader` env (`rhenvs/grader.py`) is the single-turn grader-metadata environment: a request plus a `<_grader>` block. A family (rhenvs's `configs/grader/families/<family>.yaml`) is two mirrored sides, each with a request, the grader that rewards its answers, and for word answers the answer list of that side. `hack` prompts carry the other side's grader, `clean` the side's own, `none` no metadata; cheat is an answer belonging to the other side, None for an answer on neither. Families: `parity` (even / odd), `pets_listed` (household pet / dangerous wild animal, the rewarded answers listed in the grader), `sign` (positive / negative integer, 0 neither), `letter` (vowel / consonant, y neither), `weekday` (weekday / weekend day). Record labels: `family`, `side`, `prompts`, `sys`, `cheat` (the record's top-level `family`, `system` and `prompts` are the run's arguments, `family` possibly `all`).
- `grader_lens.py`: kernel cell script, GPU box for the 27B. Constants (the parity prompts, dirs, `load_rollouts`) plus flag-gated cells, no other helpers: every cell is a flat sequence of load, compute, save, plot, print so any line can be commented out, and the model-facing work is in `utils.py`. It never samples a dataset: `load_rollouts(tag)` reads the parity family's hack-prompt records from `data/inspect/grader/` (default config, condition none, the system prompt named by the tag). Cells: j-lens cluster readouts (`mechtools.lens`, lenses from `camilablank/workspace-lenses`) at the grader tokens and along one sampled completion; prompt-difference directions (a hack prompt's last-position residual with the control prompts' span rejected, per layer); a single reasoning-on completion under add or projection hooks; a harvest cell computing each (tag, side, class) group's per-rollout CoT means from the records' served token ids (`cot_means`, cpu tensors, stripped variants with the system turn cut out of the ids); extract cells that are arithmetic on those: cheat minus clean within each side averaged over the two sides (`grader_parity_cheat_vs_clean`, the `_generic[_stripped]` and `very_hacker_cheat_vs_generic_clean[_stripped]` variants) and the whole-set means and their difference (`grader_parity_<tag>_mean[_stripped]`, `grader_parity_very_hacker_vs_generic[_stripped]`); a cell needing no rollouts: the last-prompt-token resid_post with thinking off under the very_hacker minus the generic system prompt, averaged over the two hack prompts (`grader_parity_very_hacker_vs_generic_prompt`); a j-lens readout of a saved vector; and a steered "what are you thinking about" completion. All vectors are saved to `data/vectors/<model>/` with `utils.save_vector`. Hack rates under an intervention come from a run's intervention fields (`EvalCfg` in `run.py`), not from this script. A positive add induces hacking (alpha x the gap for a saved vector); suppression is either the projection or a negative add, whose dose, random-direction control and family transfer are the runs in `ablations.py`.
- `probe.py`: kernel cell script, a side project to the orthogonalization work: saved directions used as probes. Its own model load, dirs and copy of `load_rollouts`. One cell: one no-system-prompt parity rollout (cheating or clean) shown token by token, each token shaded by its resid_post at one layer dotted with the vector's unit row at that layer.
- `nocot_dom.py`: difference-of-means directions from the reasoning-off grader records, hack minus clean over the main families, at the last prompt token (`nocot_dom_last`) and over the response tokens (`nocot_dom_resp`), one unit direction per layer of 30-63 pinned at `grader_proj`'s mean residual. Served as rows `domlast` and `domresp` through `scripts/vllm_proj.py`, every position; `domlast_heldout` and `domresp_heldout` in `run.py` are their reasoning-on runs on the held-out families, against `heldout38`, and `domlast_main` and `domresp_main` on the families they were fit on, against `main38`.
- `mbpp_dom.py`: flat script, GPU box with vLLM stopped: Will's `M_paired__cot_last` recipe on our MBPP rollouts (the cheating and honest-correct base rollouts of `mbpp38` and `mbpp38_x4`, bool corruptions dropped, train and validation splits for the fit, test split for the check): per task with both classes the mean cheating minus the mean honest residual at the newline before `</think>`, averaged over tasks, unit rows at decoder layers 40-63 pinned at the task-balanced honest mean, saved as `mbpp_dom` with `mbpp_dom_rand` (random unit rows, same pin) in `train_vector.py`'s layout, and `mbpp_dom_all` and `mbpp_dom_all_rand`, the same at every decoder layer 0-63 (the sidecar's test-split AUROC and pair fraction cover all 64 layers). Served through `scripts/vllm_proj.py` at every position as rows `mproj`, `mprojrand`, `mprojall` and `mprojallrand`; `mproj_*`, `mprojrand_*`, `mprojall_*` and `mprojallrand_*` in `run.py` are their runs (heldout, mbpp, and for the direction rows none and clean).
- `train_lora.py`: kernel cell script, GPU box with vLLM stopped: the weight-training baseline for the trained projection directions. `train_vector.py`'s KTO recipe (ENV mbpp: `mbpp_kto`'s rows and neutrals; ENV grader: `grader_kto`'s, Will's s9-gr rows with the `none38` and `clean38` base rollouts as neutrals) with the same loss, steps and seed, training a rank-16 PEFT LoRA on every linear layer of the 64 decoder layers (fp32 adapter, lr 1e-4, every position) instead of a direction; the base model is the adapter off. No terminal_verifier rollout is trained on. It saves an adapter at steps 4, 8, 16 and 24, every 40 steps and at the end under `data/loras/Qwen3.8-27B/<env>_kto_lora/step_<n>/` (weights gitignored), then reloads and scores each on the held-out pairs and neutrals (`held_out.json`, which names the step whose neutral token KL is nearest the direction's) and writes `held_pairs.json`; SMOKE runs every cell on a few rollouts. `scripts/lora_check.py` scores those pairs through a served adapter against `held_out.json`. An adapter is served by `POST /v1/load_lora_adapter` on `scripts/serve_lora.sh`'s `cb_base` server (vLLM without vllm-lens, so not eager) and selected by `EvalCfg.lora`; `mbpplora_*` and `graderlora_*` in `run.py` are their runs (heldout, mbpp, correct, the four terminal_verifier runs, secret, none and clean, and `graderlora_main`), with `kto_main` and `kto_heldout` the projection side of the grader ladder.
- `kto_sweep.py` and `kto_cfgs.py`: the sweep over `train_vector.py`'s KTO projection direction, GPU box with vLLM stopped. `kto_cfgs.py` holds `SweepCfg` (one flat dataclass: trained env, neutral envs, hooked layers, per-layer or shared direction, rank, removal scale, clamp, learned pin offset, `shift` (steering by a learned step in place of the projection), hooked positions, loss settings, steps, length cap, seed, init) and the named instances, a variant a `replace` of another. `kto_sweep.py` is a flat script with stages: `prep` (one base pass over every rollout: reference log-probs and per-env pin sums, `acts/kto_sweep/base.pt`), `run` (the worker: every name in `acts/kto_sweep/queue.txt` without a line in `results.jsonl` is trained and screened, `kto_cfgs.py` re-imported before each, parameters saved to `acts/kto_sweep/vecs/<name>.pt`), `table`, and `export <name> <out>` (the hook file `scripts/vllm_proj.py` serves). The hook is `h <- h - scale * g((h - mu_L).u - c_L sigma_L) u` at the hooked generated tokens. The worker keeps each rollout's residual entering layer 30 in memory and runs only layers 30-63 for configs hooking no earlier layer, without gradient checkpointing when the length cap is 2,500 or less. The screen is teacher-forced on base rollouts: per-token log-prob gains of honest and cheating completions (`grader_eval`, `heldout`, `mbpp_short`, `mbpp_test` under `full`), neutral token KL and gain (grader, MBPP correct-test, terminal_verifier possible, honest secret_number turns), and the decision-turn sets `tv_turn` and `secret_turn` (a cheating rollout cut at the end of its first cheating turn and scored on that turn; envs never trained on, base secret_number games read from `acts/kto_sweep/secret_base.jsonl`). `scripts/kto_served_check.py` compares a served row with the screen on the same rollouts. `b1` (grader and MBPP together, 800 alternating steps) is served as row `b1` (`cb_b1`); `b1_*` in `run.py` are its runs, and `mbppkto_secret128` and `kto_secret128` the saved directions on the first 128 games of `secret38`. The directions' rows are served without Will's stack: on the box `scripts/kto_serve_setup.sh` installs vLLM 0.32.0 with `scripts/vllm_proj.py` as a plugin, and `bash ~/serve_row.sh <row> [vision]` (`scripts/kto_serve_row.sh`) serves the base weights as `cb_<row>` with the hook file `~/hooks/<row>.safetensors`; row `base` has no hook and keeps its own compile cache, since vLLM's cached compiled graph does not know about the hook. `scripts/cheatbench_row.sh` runs one CheatBench row (9 tasks, 122 episodes) on the CheatBench VM against a served row; the verdicts come from Will's `scripts/cheatbench_judge_openrouter.py`, and `scripts/cheatbench_table.py` tabulates them.
- `prompt_dom.py`: kernel cell script, completion-less differences on the main grader families: one forward pass per family, side, prompt kind, system prompt (none, generic, very_hacker) and reasoning setting, saved as ids and bf16 resid_post at every layer and position in `acts/prompt_dom.pt` (reasoning on at effort low, the setting of the 3.8 runs), then J-lens readouts of diffs of those at `</think>` (position -2) and the newlines after it (-1), lens layers 1-62, and oracle-lens readouts of them (`mechtools.olens`, the Qwen3.6-27B lens on a second copy of the 3.8 weights, layers 20-40, with a random direction as the control). `very_hacker` minus `generic` on hack prompts is then a probe on `main38`: per-token dots at every layer saved in `acts/prompt_dom_probe.pt` with 20 random directions, within-cell AUROC by layer and by tenth of the CoT, and token strips of cheat and clean pairs.
- `cot_probe.py`: kernel cell script, a linear probe on single CoT tokens: one token's residual at one layer in, the rollout's cheat label out. Will's s9-gr rows of the five training families, `pets` as an unseen sixth; `download`, `harvest` and `fit_probes` run once and later cells read `acts/` (box only) and `data/vectors/<model>/cot_probe.*`. On the box it lives in `/root/probe`, kernel `ortho-probe`, so the real `mechtools` is imported, not `/root/ortho_train`'s stand-in. `grader_kto` is the second readout: no fit, each token's residual minus the hook's pin along the direction, at the dev-best row in the hook's window (`score_kto`). `mbpp_kto` is the third, read the same way from the saved activations with its sign flipped (`score_mkto`, no model), on grader rollouts only. The last cells show held-out rollouts token by token under either readout, in same-prompt cheat and clean pairs per cell, score base MBPP rollouts (one per task, so unpaired) (`score_mbpp` needs the model), and save it all as one page with a fixed three-way button switching readouts.
- `joint_probe.py`: kernel cell script, the same single-token outcome probe fit on two envs at once: Will's s9-gr rows of the five training families and the paired MBPP base rollouts (`mbpp38`, `mbpp38_x4`: cheating or honest and correct, bool corruptions dropped, only tasks with both classes, the test split held out, a fifth of the other tasks as dev), each env half of the loss, every (cell, class) and every rollout weighing the same within it, a cell being a grader family and side or an MBPP task. A grader-only and an MBPP-only probe are fit the same way as references, each with its own row and L2 weight chosen on dev. `harvest`, `fit_probes`, `evaluate` and `score` need the box (`acts/joint_probe/row*.safetensors` are box only); `score` reads the joint probe's logit at every position of whole rollouts through a hook at its layer (the held-out grader and MBPP rollouts, `heldout38`, `secret38`) into `acts/joint_probe/scores_<set>.pt`, and the last two cells, which run on the laptop, give the AUROCs on `heldout38` and `secret38` and write the token-strip page to `~/wgmn/artifacts/`. The probes are `data/vectors/<model>/joint_probe.*` (`w`, `b` the joint probe, `<env>_only_w`, `<env>_only_b` the references).
- `scoreboard_page.py`: every intervention's cheating cut and capability change against its own base, from the records and Terminal-Bench jobs, with Will's rows as cited constants; fills `scoreboard_template.html` (the charts, vanilla JS and inline SVG) and writes one page to `~/wgmn/artifacts/`.
- `oss_nocot.py`: the grader families on gpt-oss-120b with no reasoning, through OpenRouter rather than Inspect, a flat script writing `data/openrouter/gpt-oss-120b_nothink.jsonl`. The chat endpoints refuse to turn reasoning off, so each request is a raw completion of the harmony template with the final channel opened, pinned to DeepInfra bf16.
- `jlens_gain.py`: flat script, CPU and the local GPU: the Jacobian gain `||J_L v||` and the logit gain `||W_U diag(1 + w) J_L v||` of every saved direction through the Qwen3.6-27B J-lens (row r of the train_vector layout is resid_pre r and goes through `J_r`), against random unit directions at every layer and, at every fourth layer, both models' MLP decoder and encoder directions, pullbacks `J_L^T` of the unembedding's cluster centroids and of random vectors, and the pins. Weights come one tensor at a time by byte range into `acts/weights`; it writes `data/vectors/Qwen3.8-27B/jlens/jlens_gain.{json,html}`.
- `fd_gain.py`: flat script with `prep` (laptop), `smoke` and `run` (box, vLLM stopped) and `analyze` (laptop) stages: finite-difference sensitivity of Qwen3.8 in our own rollouts. - `nocot_readout.py`: flat script with `prep` (laptop), `run` (box, vLLM stopped), `analyze` and `rows` (laptop) stages: do directions fit on reasoning-on rollouts read or move reasoning-off grader cheating.
